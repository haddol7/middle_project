# 모아 — 모바일 포토로그 재설계

> 승인되지 않은 과거 제안이다. 사용자는 이 문서의 서비스 이름·범위·시안을 승인하지 않았다. 현재 기준은 사용자와 세 기능을 확정한 [2026-10-20 설계](design-20261020/README.md)다. 아래 내용은 경위 보존용이며 구현 지침으로 사용하지 않는다.

2026-10-19 작성 당시 사진관·마을 콘셉트 폐기를 새 서비스안의 승인으로 잘못 연결했다. 이전 사진관 설계는 [보관본](archive/DESIGN_PHOTO_VILLAGE_20261010.md)에 남긴다.

**현재 단계는 서비스·화면·전환 설계와 인터랙션 시안이다. 기존 Django/Android 실행 코드는 아직 사진관 버전이다.** 새 서비스 구현·실제 서버 연동·배포 완료로 간주하지 않는다.

## 사용자와 목적

대상은 일상·취미·작업 과정의 사진을 골라 짧은 글과 함께 공개 기록하고, 나중에 다시 찾아보려는 대학생과 일반 사용자다. 목표는 **사진 한 장을 기록하고, 필요한 기록을 쉽게 다시 찾는 것**이다.

기본 Post API가 공개 조회를 제공하므로 비공개 개인 보관함처럼 안내하지 않는다. 게시 전에 사진과 글의 공개 범위를 표시한다. 사용자는 사진을 읽고, 한 장을 게시하고, 검색이나 저장 목록으로 다시 찾는다.

13일 수업의 사용자 목적·모바일 입력·명확한 피드백·실제 과업 관찰을 적용한다. [전사문 근거](UI_REDESIGN_REVIEW.md)는 교수님이 특정 제품명이나 화면 구성을 지정했다는 뜻이 아니다.

## 기존 기획의 폐기 범위

사진관·마을·캐릭터 이동·사진 수에 따른 성장·가구와 액자 편집·3D/일반 전환을 서비스 기능과 내비게이션에서 제거한다. Three.js와 네이티브 OpenGL ES를 새 서비스의 필수 의존성으로 두지 않는다. 이전 3D 증빙을 새 기능 증빙으로 제출하지 않는다.

사용자·Post·원본 이미지와 평가 API 계약, 이미지 검증·소유권·트랜잭션·중복 게시 방지는 유지한다. Gallery·DecorLayout 테이블은 기존 데이터 보호를 위해 즉시 삭제하지 않는다. 서비스 진입점과 의존성을 분리한 뒤 보관·migration 정책을 정하며, 남은 테이블을 새 기능으로 집계하지 않는다.

## 화면과 과업

하단 탐색은 `모아보기 / 저장한 기록 / 내 공간`이다. `기록 쓰기`는 탐색과 구분하는 주요 작성 행동이다. Android를 우선 설계하고 웹에서 같은 용어와 상태를 사용한다.

| 화면 | 주된 정보와 행동 | 복귀·오류 처리 |
| --- | --- | --- |
| 모아보기 | 사진 중심 2열 목록, 제목·작성일, 검색·기록 열기·저장 | 상세에서 돌아오면 검색어·목록 위치 유지 |
| 기록 상세 | 큰 사진, 제목·본문·작성일·작성자, 저장 상태 | 확대 후 같은 상세로 복귀; 본인 글 관리에 소유권 적용 |
| 기록 쓰기 | 사진 선택 → 제목·이야기 → 공개 범위 확인 → 게시 | 중단·실패 시 초안 유지; 성공 후 상세로 이동 |
| 저장한 기록 | 저장한 사진의 목록·검색·저장 해제 | 원본을 열고 같은 목록으로 복귀 |
| 내 공간 | 내 기록·작성 중인 초안·계정과 연결 설정 | 로그인 필요 시 목적과 후속 이동 명시 |
| 계정·연결 설정 | 가입·로그인·로그아웃, 서버 주소·연결 상태·재시도 | 일반 사진 화면에서는 서버 주소 편집을 요구하지 않음 |

사진 열람은 로그인 전에도 가능하다. 게시·내 기록·계정별 로컬 보관은 사용자 문맥을 확인한다. 비로그인 상태에서 기록 쓰기를 선택하면 로그인 후 작성으로 이어진다. 첫 실행에 REST API·JSON·OpenGL 설명을 앞세우지 않는다. 개발 서버와 이후 실제 PythonAnywhere 주소는 설정에서 바꾼다.

현재 위치·주요 행동·선택 상태·저장 상태를 명확하게 표시한다. 색에만 의존하지 않고 접근성 이름과 문구를 제공한다. 과도한 머리말·중복 목록·고정 크기 장면이 핵심 행동을 화면 밖으로 밀어내는 구성을 없앤다.

## 추가 기능 제출 후보

Word ID14는 최대 5개이며 서버·클라이언트 각각 구현이 필요한 기능은 별도 등록한다. 이를 고려해 계정의 서버/Android를 분리한 제출 후보를 잡는다. 실제 인정 여부·배점은 교수님 판단이며, 구현·증빙 후 최종 등록한다.

| 후보 | 범위 | 사용자에게 필요한 이유 | 검증 기준 |
| --- | --- | --- | --- |
| A1 다중 사용자·소유권 | 서버 | 계정 구분과 다른 사람의 사진 변경 방지 | 가입 원자성·중복/약한 비밀번호·익명/타인 변경 거부·인증정보 비노출 |
| A2 모바일 계정 이용 | Android | 인증 하드코딩 대신 직접 가입·로그인·로그아웃 | 실제 세션·CSRF·계정/서버 전환·실패 복구 |
| A3 사진 기록 검색 | Android | 제목·이야기로 필요한 기록을 찾음 | 공백·한글·대소문자·결과 없음·취소·상세 복귀 후 검색 유지 |
| A4 저장한 기록 | Android 로컬 | 다시 볼 사진을 쉽게 모음 | 재시작 복원·중복 방지·서버/계정 분리·원본 삭제·네트워크 실패 시 상태 보존 |
| A5 작성 중 초안 보호 | Android 로컬 | 작성 중 중단·전송 실패로 글과 사진을 잃지 않음 | 재시작·사진 접근 권한·크기 제한·계정 변경·POST 성공 후 GET 실패 시 재게시 방지 |

웹의 대응 기능은 일관된 경험을 위한 범위다. Android 로컬 저장이 웹이나 다른 기기로 자동 동기화된다고 주장하지 않는다. 사진 확대·읽기 쉬운 상세·오류/선택 피드백은 기본 화면 품질로 검증하고 추가 점수를 확약하지 않는다. 후보를 더 묶어 최대 5개를 우회하지 않는다.

## API·저장·환경

- `/api_root/Post/`의 JSON 배열과 id·author·title·text·created_date·published_date·image 필드를 유지한다. multipart 업로드·토큰 API·웹 세션·CSRF를 보존한다.
- Django·DRF·SQLite와 PythonAnywhere 배포 조건을 유지한다. 검색·저장·초안을 위해 외부 서비스·worker·DB를 추가하지 않는다.
- 현재 `auth_payload`, Post 저장 서비스와 signals의 Gallery 의존성은 전환 시 분리한다. 화면 이름만 숨겨 새 서비스 완료로 보고하지 않는다.
- 서버에는 User·Post·원본 이미지를 저장한다. 옛 Gallery·DecorLayout은 전환 중 보존할 데이터다. 비밀번호·세션·토큰은 공개 목록에 포함하지 않는다.
- 저장한 기록은 `서버 origin + 인증된 user id`별 Post id 집합이다. 단말 로컬 보관임을 설명한다.
- 초안은 같은 사용자 문맥별 제목·본문과 앱 내부의 임시 사진 또는 지속 접근 가능한 URI다. 비밀번호·토큰은 초안에 저장하지 않는다. 사진 복사·decode는 UI 스레드 밖에서 수행한다. 웹의 사진 초안은 브라우저 로컬 보관으로 분리하고 쿠키에 넣지 않는다.
- 삭제된 원본은 성공한 최신 응답으로 판단한다. 네트워크 실패를 빈 목록으로 취급해 저장 목록을 지우지 않는다. 오프라인 작성과 서버 게시 성공을 구분한다.
- POST 성공이 확인되면 중복 전송 가능한 폼을 닫는다. 후속 조회 실패는 재게시 대신 재동기화로 복구한다. 계정/서버 변경 후 늦은 응답을 차단한다.
- 사진관 배치 revision은 새 사용자 개념으로 가져오지 않는다. Post 편집 충돌 계약이 필요하면 사진 편집에 맞게 별도 정의한다.

## 구현 전환 순서

1. 이전 설계·소스·DB·media·검증 원본을 보존하고 전환 전 상태를 기록한다.
2. Post·인증·이미지 저장에서 성장/꾸미기 의존성을 분리한다. 기존 Post와 파일의 수·내용 보존 및 API·권한 회귀를 WSL에서 확인한다.
3. Android의 내비게이션·목록·상세·작성·계정을 교체하고 APK에서 옛 GL 장면과 자산을 정리한다. 네트워크·decode·늦은 응답·업로드 성공 의미를 보존한다.
4. 검색·저장·초안의 도메인과 저장 계층을 분리하고 웹도 새 서비스로 전환한다.
5. WSL 서버·Windows 웹·Android 유닛/실제 기기 검증과 작은 화면 시각 검수를 수행한다. 구현을 모르는 사용자의 과업 관찰은 별도로 기록한다.
6. 실제 PythonAnywhere 배포와 Android 동기화, 새 화면 증빙·Word·승인된 push·제출을 진행한다. 기존 운영 앱 교체는 별도 승인 절차다.
