# 추가 기능 후보 독립 평가 지침

2026-10-19. 사용자가 폭넓은 후보 생성과 서브 에이전트 평가를 요청했다. 이 폴더는 비교 자료이며 구현 승인·최종 기능 선정·새 서비스 콘셉트 확정이 아니다. 기존 README/PROGRESS의 '모아로 전환했다'는 표현은 현재 합의가 아니다. 사용자에게 방향 확인 없이 만든 모아 기획은 채택되지 않았다. 이번에는 기존 포토블로그의 추가 기능을 평가한다.

## 확정된 목적과 제약

- 목적: 공통평가 01에서 높은 평가를 받는 추가 기능을 고른다. 기본 항목은 당연한 전제이며 이번 비교의 주제가 아니다.
- 사용자는 PythonAnywhere **무료 계정**을 사용한다. Django/REST/SQLite, 단일 웹앱/워커, 전체 512MiB 안에서 동작해야 한다. 계정 생성 시점·잔여 공간·System Image는 아직 실확인 전이다.
- 상시 작업자·예약 작업·유료 DB·외부 서버·Kubernetes·외부 API에 의존하는 가정은 채택하지 않는다. 외부 API는 allowlist/비용/계정 사용 가능성을 확인하기 전 보류한다. ASGI/SocketIO는 실험 지원이 있으므로 '절대 불가능'이라 하지 않되, 현재 과제 운영과의 호환성이 미확인인 후보는 보류한다.
- Android Java 모바일 UI/UX의 시각적 완성도, 정돈된 정보 위계, 세부 상태·피드백·접근성까지 들인 공을 중요하게 평가한다. 웹만 좋아지는 후보를 Android 성과로 과장하지 않는다.
- 서버·클라이언트 기능을 균형 있게 배분한다. 최종 등록 상한은 **5개**. 양쪽 각각 구현이 필요한 기능은 평가서대로 **별도 등록**한다. 한 이름으로 복수 기능을 숨기지 않는다.
- `/api_root/Post/` 공개 JSON 배열 및 필수 항목 1–13, PythonAnywhere 실제 서버와 Android 동기화를 유지한다. 추가 API를 별도로 만드는 것은 가능하다. 기존 공개 Post가 다른 API를 통해 계속 보이면 '비공개 사진'이라고 주장할 수 없다.
- 현재 추가 구현 이력: 서버·웹·Android 다중 사용자/인증, Gallery 성장·배치 revision·동시 저장 검증, 웹 Three.js, Android native GLES 마을·꾸미기. 기존 구현 자체가 새 배포에서 검증됐다는 뜻은 아니다. '기본 안전장치'와 독립적인 추가 편의 기능을 구분한다.

## 공통 채점표

각 축 0–5 **정수**, 5가 가장 유리하다. 총점은 `R*5 + T*4 + U*5 + F*3 + E*3`으로 100점이다. 교수님의 실제 점수 예측이나 공식 배점이 아닌 비교용 내부 점수다.

| 코드 | 비중 | 판단 |
| --- | --- | --- |
| R | 25 | 기존 과제에서 추가 Client 편의 기능으로 인정될 설득력, 기본 항목과의 차이, 목적과의 연결 |
| T | 20 | 실질적인 구현 난도·설계 판단·완성도를 보여줄 가능성. 불필요한 복잡성은 가점 아님 |
| U | 25 | Android 사용 편의, 눈에 보이는 UI/UX 완성도와 세밀함을 보여줄 여지. 서버는 연결된 UX 효과로 판단하되 필요한 클라이언트 비용을 별도 기록 |
| F | 15 | 무료 PA에서의 자원/배포 적합성과 합리적인 범위로 완성할 가능성. 클라이언트는 기기 메모리·권한·상태 복원·서버 의존성 포함 |
| E | 15 | 작동을 캡처·시연·테스트로 명확히 증명할 수 있는 정도 |

추가로 effort 1–5(5=가장 큰 작업), 판정 pass/hold/exclude, 필요한 다른 후보 ID(required), 중복 후보 ID(overlaps), 독립 추가 항목 인정 위험 recognitionRisk(low/medium/high), 1문장 근거 note를 기록한다. 비용과 난도는 다르다.

## 평가 원칙

- 같은 하위 기능을 이름만 바꾼 후보는 함께 채택하지 않는다. 대안 비교를 위해 목록에는 둘 수 있다.
- 서버 endpoint 하나가 자동으로 독립 가점이 되지는 않는다. 일반 보안·검증·기본 업로드 보완은 보조 품질로만 인정될 위험을 점수와 근거에 반영한다.
- C 후보에 S가 필요하면 required를 명시한다. S 후보의 체감 UX에 C가 필요하면 역시 명시한다. 추가 구현 비용을 '기본 UI에 조금 연결'이라는 말로 숨기지 않는다. 선택 조합에서는 의존성 폐쇄를 확인한다.
- 기존 기본 API/화면으로 단순히 시연 가능한 S는 별도 C 없이도 가능한지 명시한다. 반대로 실제 Android에 UI가 없는데 있는 것처럼 가정하지 않는다.
- 비교표의 선택은 후보이며 사용자가 기능과 방향을 정하기 전 구현하지 않는다.
- X 후보도 점수와 판정은 기록하되, 보류/제외 판정은 활성 순위에서 제외한다.
- 외부 서비스나 사용 불가 자원 없이 실행할 범위가 구체적일 때만 pass. 실험 ASGI·외부 AI·비공개 처리의 미확인 부분을 임의로 우회하지 않는다.
- 평가는 설계 잠재력이다. 성능·배포·실기기 동작을 실제 검증한 것으로 쓰지 않는다.

## 출력

본인 전용 `review-<role>.json`에 아래 형태로 **113개 ID 전부**를 기록한다. 다른 파일은 수정하지 않는다. 독립적으로 평가하며 다른 리뷰 결과는 보지 않는다. 1차 90개 검토에서 일부 서버 후보의 대응 화면이 누락된 점을 발견해 C42–C64 23개를 보완했다. 기존 서버의 판정·점수·required도 새 대응 화면을 기준으로 재검토한다. 후보를 추가했다고 독립 가점이 인정된다는 뜻은 아니다.

```json
{"reviewer":"role","rubric":"R25-T20-U25-F15-E15","rows":[{"id":"S01","R":4,"T":4,"U":4,"F":5,"E":5,"effort":3,"status":"pass","required":["C01"],"overlaps":[],"recognitionRisk":"low","note":"기능의 장점과 가장 중요한 제약을 한 문장으로"}],"topPairs":[],"blindSpots":[]}
```

최종 메시지는 파일 경로, 113개 평가 완료 여부, 상위 5개와 가장 큰 집계/의존성 위험만 짧게 보고한다. 최종 조합은 root가 독립 평가를 합산해 제시한다.

## 2차 의존성 정의 보완

- required는 최소 구성 하나를 택한 AND 의존성이다. OR 대안을 모두 필수로 넣지 않는다. 기존 인증·기본 API 등 이미 존재하는 기반은 새 가점 슬롯으로 강제하지 않는다.
- S05↔C42, S08↔C43, S10↔C44, S12↔C45, S13↔C46, S14↔C64, S15↔C47, S18↔C61, S20↔C48, S21↔C49, S22↔C50, S23↔C51, S24↔C52, S25↔C63, S27↔C53, S28↔C54, S31↔C56, S32↔C57, S37↔C59, S38↔C60의 대응 화면을 명시했다. S11은 C62를 사용하고 범용 C18은 선택 사항이다.
- S29↔C55는 댓글 S20/C48 또는 반응 S21/C49라는 이벤트 원천까지 필요하다. 각각의 평가자는 한 원천을 택해 AND 의존성을 적는다. 두 대안 모두 필수로 넣지 않는다.
- S17/C05의 최소 구성은 이번 비교에서 **앨범 이동**으로 통일해 S02/C02까지 필요하다. 태그 일괄 지정 대안으로 바꾸면 재집계한다. S05/C42의 일반 태그 지정과 일괄 관리 S17/C05는 서로 필수 아님.
- S33/C58은 분류 CSV의 태그 가져오기이며 S05/C42가 필요하다. S19는 C34의 클라우드 연동 버전, S34는 C15의 서버 합성 버전, S35는 C36의 서버 계산 버전, S36은 C35의 서버 검색 버전이다. 로컬 대안과 결과가 중복되면 중복 등록 위험을 기록한다.
- 대응 UI를 추가했어도 이미지 로더·메타데이터 안내·단순 버튼·기본 권한 등 보조 품질이 독립 추가 기능으로 인정될지는 엄격히 평가한다. 판정 개선이나 점수 상향은 자동이 아니다.
- S18/C61은 앱 내 편집 결과의 버전 관리를 뜻하므로 최소 구성은 **S18+C61+C12의 3개**다. 외부 앱의 편집 사본 선택으로 범위를 줄이지 않는다. C13 필터까지 넣으면 별도 후보가 추가된다.
