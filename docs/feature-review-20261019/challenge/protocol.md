# 도전성 중심 재평가 — 사용자 추가 조건

2026-10-19. 사용자가 구현 현실성 기준을 빼고, 어려운 구현에 높은 점수를 주도록 재평가를 요청했다. 동시에 **Codex가 구현할 구체적 경로가 있어야 하며, 사용자가 직접 설치·개발 지식 학습·모델 학습·강화학습을 수행해야 하는 후보는 허용하지 않는다**고 명시했다. 기존 평가 결과는 보존한다. 기능 선정·구현 승인이 아니다.

## 입력과 고정 조건

- 후보: 상위 폴더 `candidates.psv`의 113개 전부. 같은 정의를 비교한다. 기능을 몰래 축소하거나 기본 업로드를 새 기능으로 집계하지 않는다.
- 원본 과제 및 의존성 규칙: 상위 `protocol.md`의 평가서 ID14 최대 5개와 서버/클라이언트 별도 집계, 의존성 보완 사항을 유지한다. **상위 지침의 F 점수·effort·구현 부담·검증 용이성 감점은 이번 평가에서 폐기한다.**
- 기본 과제 ID1–13, 공개 Post 배열, 실제 PythonAnywhere 서버·Android 동기화를 보존한다. 무료 PA의 단일 앱/워커·512MiB·외부 통신·상시 작업 제약은 점수가 아니라 채택 자격 조건이다. 불가능/미확인 환경을 높은 난도라는 이유로 채택하지 않는다.
- 모아 기획은 확정되지 않았다. 사진관·마을은 이전 비교군이며 자동으로 새 방향에 복귀시키지 않는다.

## 새 점수

각 축은 **0–10, 0.5 단위 허용**. 점수는 `T*5 + U*2.5 + R*2 + V*0.5`, 100점 만점이며 교수님 공식 배점이 아닌 내부 비교다.

| 코드 | 비중 | 판단 |
| --- | --- | --- |
| T | 50 | 기술적 도전성. 알고리즘·수학/이미지 처리·동시성·오프라인 동기화·실패 의미·복잡한 상태/상호작용 등 실제 구현 난도. 어려움에 높은 점수를 준다. 작업량이 많다는 이유로 감점하지 않는다. 불필요하게 복잡하게 만든 구현에는 보너스를 주지 않는다 |
| U | 25 | 완성했을 때 Android 사용 편의·시각적 완성도·세밀한 조작과 피드백을 보여줄 잠재력. 화면이 많거나 마감이 어렵다는 이유로 감점하지 않는다 |
| R | 20 | 추가 편의 기능으로 평가받을 설득력, 기본 항목과의 차이, 과제 목적과의 연결. 독립 기능 인정/서버·클라이언트 집계 위험은 유지 |
| V | 5 | 완성한 결과의 차별성과 기술/사용 효과를 테스트·시연·증빙으로 명확히 드러낼 수 있는 정도. **테스트 만들기 어렵다/시간이 오래 걸린다**는 감점 사유가 아니다 |

현실성 F 점수와 effort는 새 점수에 넣지 않는다. 보류/제외 또는 동점 처리에서도 일정·작업량·학습 난도를 은밀히 감점하지 않는다. 동점은 리뷰어 최저 총점, T 평균, R 평균, ID 순으로 정렬한다.

## Codex 수행 가능성 — 필수 자격 심사

각 후보마다 아래를 점수와 별개로 검사한다.

1. **구현 경로**: 구현할 알고리즘/데이터 구조/플랫폼 API가 구체적인가. 'AI가 알아서 한다'만으로 통과시키지 않는다.
2. **설치와 구성**: 기존 환경 또는 Codex가 명령·Gradle·venv 등으로 자동 구성할 수 있는 공개 의존성인가. 사용자에게 수동 설치·별도 프로그램 숙련을 요구하지 않는다. 프로젝트 범위의 일반 라이브러리 자동 설치는 가능하다.
3. **학습/훈련**: 사용자 공부·데이터 수집/라벨링·개인 모델 학습·강화학습이 필수면 보류/제외한다. 해시·기하 변환·SQL·색상 통계·수작업 없는 합성 fixture 검증은 모델 훈련이 아니다. 사전학습 모델도 자동 취득/라이선스/실행 환경/오프라인 동작이 확인되지 않으면 보류한다.
4. **검증 경로**: Codex가 생성한 합성 사진/DB fixture, WSL 테스트, Windows Gradle·JUnit·ADB/에뮬레이터로 검증할 구체적 방법이 있는가. 사용자만 조작할 수 있는 별도 하드웨어/유료 서비스가 필수면 보류한다. 일반 제품 사용자가 사진을 선택하는 동작과 개발자가 수동으로 설치·훈련하는 일을 혼동하지 않는다.
5. **실행 환경**: 무료 PA와 현재 과제에서 핵심 서버가 실제 동작할 구조인가. 외부 GPU/worker/Kubernetes·유료 API·미확인 ASGI로 우회하지 않는다.

기존 계정 인증·배포 권한 승인 절차는 개발 수작업이나 모델 훈련과 다르다. 계정에 아직 로그인하지 않았다는 이유만으로 모든 서버 기능을 탈락시키지 않되, 실제 배포를 검증 완료라고 쓰지 않는다. 새 외부 계정/API키·비용이 필수이고 사용자 작업이 없으면 구성할 수 없다면 보류한다.

`codexGate`와 `platformGate`: pass/hold/exclude. 이것은 구체적 구현 경로 검토이며 새 기능 구현 완료나 무결점 성공 보장이 아니다. 근거 부족을 막연한 Codex 가능성 주장으로 덮지 않는다. 두 gate가 모두 pass이고 기본 항목 중복이 없을 때만 status pass를 줄 수 있다.

## 이미 확보된 도구와 근거

- WSL Ubuntu, `/home/daeha/.venvs/mobile_web_service`, Python 3.12.15, 프로젝트 Django/DRF/Pillow/SQLite 의존성이 설치돼 있다. Python/backend 검증은 WSL에서 수행한다.
- Windows Android Studio/JBR, SDK36, API35 emulator, ADB, Gradle wrapper와 Java Android 프로젝트가 있다. 기존 빌드·기기 테스트 경로는 `common01/PhotoViewer/tools/verify-android.ps1`, `tools/local/android-env.ps1`이다. 구현 완료 주장이 아니라 추가 기능을 개발/검증할 수 있는 도구의 근거다.

## 평가자 출력

서브 에이전트 3명은 같은 기준으로 113개 전부를 독립 재평가한다. 단순히 옛 점수에서 F를 제거하고 재가중하지 말고, U/R/V에 남아 있던 '어려워서 감점'도 제거해 다시 판단한다. 다른 평가자의 결과는 읽지 않는다.

본인 전용 `challenge/review-<role>.json`만 작성한다. role은 rubric/technical/ux. 아래 스키마의 필드를 모든 행에 넣는다.

```json
{"reviewer":"role","rubric":"T50-U25-R20-V5","rows":[{"id":"C16","T":9.5,"U":9,"R":8.5,"V":9,"status":"pass","codexGate":"pass","platformGate":"pass","userManualWork":false,"trainingRequired":false,"implementation":"네 점 기하 변환과 원근 보정 미리보기, 드래그 상태를 Java로 구현","dependencies":"기존 Android Matrix/Canvas; 사용자 설치 없음","verification":"합성 사각 격자의 역변환 오차·코너 드래그·회전/재생성 기기 테스트","required":[],"overlaps":[],"recognitionRisk":"low","note":"구현 경로와 도전성이 구체적이며 개인 모델 훈련이 필요 없다"}],"blindSpots":[]}
```

예시는 형식이며 C16의 점수를 미리 지정하는 것이 아니다. 평가자는 직접 점수를 정한다. userManualWork/trainingRequired가 true인 행은 status pass 금지. X 후보의 보류 이유를 현실성 감점과 구분한다. 기존 사진관 비교군도 같은 척도로 평가한다.

최종 전 Node로 113개 ID 중복/누락, 모든 축의 0–10/0.5 단위, gate/status 일관성, 4개 근거 문자열·note·위험도 enum·의존 ID를 검증한다. 구현 코드는 수정하지 않는다. 최종에는 파일 경로와 상위 서버/클라이언트 각 3개, Codex가 수행할 근거와 보류 사유를 짧게 보고한다.
