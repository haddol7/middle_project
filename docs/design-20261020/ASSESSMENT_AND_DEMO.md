설계자의 해석은 다음과 같다. 높은 평가를 위해서는 기본 항목과 증빙을 빠짐없이 충족한 다음, 사진 블로그에 필요한 추가 기능을 실제로 완성하고, 난이도와 사용성 개선이 어디에 있는지 이해하기 쉽게 보여줘야 한다. 단순히 기능 수나 AI 이름을 늘리는 것으로 설명을 대신하지 않는다.

기능은 A01–A03 세 개다. 등록 단위를 서로 다른 사용자 기능처럼 설명하지 않는다. E01에는 기존 이미지 업로드를 서버 추가 기능으로 다시 등록하지 않는다. E03·E05도 단순 저장 API 이름이 아니라 사용자에게 이어지는 조회·검색 행동까지 검증한다. 최종 인정과 점수는 교수님 평가다.

차별점을 설명할 기술적 근거는 자동 인식 자체 외에도 다음과 같다. A01은 확대·이동 화면의 좌표와 실제 저장 픽셀의 일치, 누락 보완·실행 취소가 필요하다. A02는 일반 라벨을 사진 블로그의 제한된 테마로 연결하고 불확실한 추천과 사용자 교정을 관리해야 한다. A03은 한글·영문 인식 결과를 원래 위치와 연결하고, 수정·제외·사진 교체 뒤에도 서버 검색이 정확한 버전만 반환해야 한다. 세 기능을 묶을 때는 모자이크 이전 정보가 검색에 남지 않도록 같은 사본을 기준으로 처리해야 한다.

OCR의 Korean·Latin 결과가 같은 줄을 중복 반환하면 동일/겹치는 위치와 정규화 문구로 합치고, 한글이 있는 줄은 Korean 결과를 우선한다. 서로 다른 문구가 겹치면 자동 합성하지 않고 확인 화면에서 선택할 수 있게 한다. 이 규칙은 모델 결과 어댑터 테스트와 실제 한영 혼합 사진으로 확인한다.

백엔드 검증 예정 명령은 WSL venv에서 `python manage.py check`, `python manage.py makemigrations --check --dry-run`, `python tools/verify_baseline.py`이며 새 내용·검색 단위/HTTP 테스트를 이 검증 경로에 추가한다. Coverage는 라인·분기·총합을 구분하고, 높은 수치를 기능 품질과 동일시하지 않는다. Android는 Windows의 `PhotoViewer/tools/verify-android.ps1 -RunDevice`로 기존 빌드·유닛·기기 회귀를 유지하며 신규 기기 검사를 추가한다. 이것들은 이번 설계 작업에서 실행한 명령이 아니다.

## 5. 모델 품질과 실제 사용성 측정

다음 수치는 **설계자가 정한 초기 검수 목표**이며 교수님 공식 기준·이미 달성한 수치가 아니다. 학습 데이터가 아니라 고정된 검증 자료를 사용한다. 동의·사용 권한이 있는 사진을 준비하고 정상·어려운 조건의 결과를 모두 남긴다. 실패를 숨기거나 잘 나온 시연 사진만으로 품질을 주장하지 않는다.

| 분류 | 자동 지원 6개 테마 각 10장 + 기타 10장 + 애매한 사진 20장; 정답·예상 기권을 사전에 표시 | 명확한 지원 사진 60장의 top-1 80% 이상(기권도 오답), 해당 집합의 자동 추천 precision 90%·coverage 60% 이상 목표; 기타·애매한 사진은 기권/오추천과 사용자 선택 경로를 별도 보고 |

| 속도 | 기준 Android API35 기기·2048px 이하 사진, 모델 첫 실행/반복 분리 | 얼굴·분류·OCR 각각 p50/p95 기록, 반복 각 p95 3초를 목표; CPU 작업 중 UI 입력 가능 |
| 서버 | 동일 SQLite, 500개 글·최대 100줄/글의 합성 테스트 데이터 | 검색 자체 p95 500ms 목표, 실제 클라우드 전체 응답은 네트워크 포함 별도 측정; 디스크 사용량 기록 |
| 첫 사용 | 가능하면 구현을 모르는 3명, 없으면 수행자·제약 명시 | 안내 없이 핵심 과업 성공 여부·시간·오조작 기록, 심각한 막힘 수정 후 재관찰 |

정확도 목표가 미달하면 원인·지원 범위·사용자 교정 경로를 기록하고 개선한다. 수동 교정만으로 자동 기능 품질을 달성했다고 보고하지 않는다. SDK confidence는 실제 확률로 해석하지 않는다. 학습·재학습·강화학습은 계획에 없다.

## 6. 3분 시연과 쉬운 설명

시연 자료는 주변 손님·음식·가게 문구가 함께 있는 사용 허가된 사진 한 장과 비교용 사진 2장이다. 제목·본문에는 검색할 가게 문구를 넣지 않는다. 실제 클라우드 URL로 연결한 앱을 사용하고, 개발 설정은 시작 전에 준비한다.

| 시간 | 조작 | 설명할 핵심 |
| --- | --- | --- |
| 0:00–0:20 | 사진 목록→올리기→후기 사진 선택 | “후기 사진에는 주변 사람과 가게 정보가 함께 찍힙니다. 게시 준비와 다시 찾기를 도와주는 세 기능입니다.” |
| 0:20–0:55 | 자동 모자이크→얼굴 하나 해제→누락 영역 직접 추가 | “찾은 얼굴은 먼저 가립니다. 사용자가 직접 보완하고, 서버에는 이 결과가 반영된 사본만 보냅니다.” |
| 0:55–1:25 | 음식 추천·태그 확인→잘못된 글자 한 곳 교정 | “사진 내용을 추천하지만 최종 결정은 사용자에게 있습니다. 사진 속 글자도 위치를 확인하며 고칠 수 있습니다.” |
| 1:25–1:50 | 게시 성공→상세→목록 재조회 | “분류와 문구는 실제 PythonAnywhere에 사진과 함께 저장되어 다시 접속해도 유지됩니다.” |
| 1:50–2:25 | 음식 필터→사진에만 있는 가게 문구 검색→일치 영역 | “글에 적지 않은 정보로도 찾고, 어떤 부분 때문에 검색됐는지 바로 확인합니다.” |
| 2:25–3:00 | 검증 자료 한 장·기본 과제 증빙 연결 | “SDK 인식에 더해 실제 픽셀, 좌표, 교정, 이미지 버전, 서버 검색의 일관성을 구현·검증했습니다.” |

시간은 발표 준비용 가정이며 공식 제한이 아니다. 기본 1–13 전체 증빙은 별도 보고서에서 빠짐없이 제공한다. 네트워크나 인식이 실패하면 실제 실패 상태와 복구 행동을 보여준다. 녹화 자료를 보조로 쓰면 녹화 시각·환경을 밝히고 현재 배포 성공을 대신했다고 말하지 않는다.

보고서의 각 추가 등록은 **불편 → 입력·조작 → 결과 → 직접 구현한 부분 → 증빙·검증 환경** 순서로 짧게 쓴다. 예를 들어 A03은 “제목·본문에 없는 간판 문구로 사진을 찾기 위해, OCR 문구를 사용자가 교정하고 서버 검색에 연결했다. 검색 결과를 열면 원래 사진의 일치 줄을 표시한다”로 설명한다. 내부 API와 모델 이름은 그 뒤에 붙인다.

## 7. 제출 증거 묶음

V01은 원본과 자동/수동 모자이크 화면, 실제 게시 이미지 및 서버 다운로드 파일 검사를 연결한다. V02는 추천·교정 화면, V03은 서버 확정값과 재조회·필터 결과, V04는 OCR 교정·검색 제외·일치 영역 화면, V05는 제목·본문에 없는 문구 검색과 교정/교체 후 검색 결과를 연결한다. 각 묶음에 코드 버전·실행 환경·테스트 ID·실제 URL·촬영 시각을 기록한다.

평가서가 요구한 실제 화면은 합성 이미지나 프로토타입 캡처로 대체하지 않는다. Word 보고서에 원본 해상도로 내장하고, 보고서를 다른 위치에 복사해도 이미지가 유지되는지 확인한다. 적·부 등 교수님 판정 칸은 대신 채점하지 않는다. 테스트 로그·Coverage·DB 검사만으로 요구된 주소창·터미널·VS Code 화면을 확보했다고 처리하지 않는다.
