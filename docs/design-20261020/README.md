# 사진 블로그 추가 기능 설계

2026-10-20 · 설계 기준본. 사용자와 확정한 세 기능을 대상으로 한다. 실행 코드 구현·배포 완료 문서가 아니다.

> 구현 후속: 실제 1인 블로그·PythonAnywhere 운영·Android 화면 및 OCR 반영을 진행했다. 현재 상태는 [프로젝트 현황](../PROJECT_STATUS.md), [Android 적용](../ANDROID_NATIVE_PARITY.md), [현재 배포](../DEPLOYMENT_CURRENT.md)를 따른다. 아래 미구현·미배포 설명과 등록 계획은 설계 시점의 기록이다.

**목적은 사진 블로그의 실제 불편을 해결하고, 기술적 도전과 사용성을 평가자가 동작 증거로 이해할 수 있게 하는 것이다.** 사진관·마을 콘셉트는 새 화면에서 사용하지 않는다. 새 서비스 이름이나 별도 콘셉트는 정하지 않았다.

## 평가 자료를 먼저 확인한 결과

최종 Word 평가서는 기본 항목의 실행과 제출 증빙을 요구한다. 추가 항목은 “기타 기획 되지 않은 Client 편의 기능 [최대 5개]”이며, 서버·클라이언트 각각 구현이 필요하면 별도 요구사항으로 등록한다고 명시한다. 기본 업로드 UI는 이미 기본 11번의 선택 항목이므로 추가 기능으로 다시 계산하지 않는다.

13일 전사문에서는 사용자와 과업을 먼저 정하고, 입력·진행·결과·오류를 포함한 UI를 고민하며, 실제 사용을 관찰하고, 기능의 목적과 의도를 설명하는 것이 중요하게 나온다. 기술 난이도와 사용성을 위해 고민한 흔적을 함께 보여줄 근거가 필요하다. 공식 수치 배점이나 특정 화면 패턴을 지시한 것으로 확대 해석하지 않는다.

이에 따라 설계의 중심을 **사진 선택 → 얼굴 확인·가리기 → 내용 정리 → 게시 → 다시 찾기**로 정했다. 기술 이름부터 나열하는 발표보다, 같은 후기 사진을 준비하고 나중에 찾는 상황으로 설명한다. 원문·시각·설계 결정의 연결은 [평가 근거와 시연 계획](ASSESSMENT_AND_DEMO.md)에 있다.

## 확정한 사용자 기능

| 기능 | 해결하는 불편 | 핵심 동작 | 평가 등록 계획 |
| --- | --- | --- | --- |
| A01 얼굴 자동 모자이크 | 후기 사진에 다른 사람의 얼굴이 함께 나옴 | 얼굴 자동 탐지·가리기, 얼굴별 해제, 누락 영역 직접 보완, 실제 게시 사본에 적용 | Android 1 |
| A02 자동 테마·태그 분류 | 매번 분류를 입력하기 번거롭고 기록이 쌓이면 찾기 어려움 | 사진 내용으로 추천, 사용자 교정, 서버 저장, 테마·태그별 조회 | Android 1 + 서버 1 |
| A03 사진 속 글자 검색 | 글에 적지 않은 간판·메뉴·책 표지 문구로 사진을 찾을 수 없음 | 한글·영문 OCR, 교정·검색 제외, 서버 검색, 사진의 일치 영역 표시 | Android 1 + 서버 1 |

사용자가 쓰는 기능은 **3개**, 평가서에 맞춘 등록 계획은 **5개**다. 이는 기능을 다섯 개처럼 포장하거나 점수를 보장한다는 뜻이 아니다. 각 서버·Android 동작과 증빙을 따로 정의한다.

## 한 사진으로 이어지는 사용 예

식당 후기 사진에 음식, 간판, 주변 손님이 함께 찍혔다. 사진을 고르면 얼굴을 자동으로 가려 보여준다. 사용자는 자기 얼굴만 해제하거나 누락된 얼굴을 직접 가린다. 확정한 게시 사본에서 음식 테마·태그와 간판 글자를 분석한다. 잘못 인식한 가게 이름을 고친 다음 제목과 본문을 적어 게시한다.

나중에는 ‘음식’ 테마로 모아 보거나 사진에만 있던 가게 이름으로 검색한다. 결과를 열면 그 문구가 있던 위치가 강조된다. 앱을 다시 실행해도 같은 분류와 검색 결과를 실제 PythonAnywhere 서버에서 받는다.

## 주요 결정

1. 얼굴 탐지·테마 추천·문자 인식은 앱에 포함한 기존 모델로 Android에서 실행한다. 별도 모델 설치·학습·강화학습을 사용자에게 요구하지 않는다.
2. PythonAnywhere 무료 서버가 실제 게시·분류 저장·검색·Android 동기화를 담당한다. 외부 핵심 서버나 백그라운드 워커는 도입하지 않는다. [무료 계정 안내](https://help.pythonanywhere.com/pages/FreeAccountsFeatures/), [웹 앱 비동기 작업 제약](https://help.pythonanywhere.com/pages/AsyncInWebApps/).
3. 원본을 서버에 먼저 보내지 않는다. 사용자가 확인한 모자이크 게시 사본을 확정하고, 그 파일에서 테마·글자를 분석한다. 업로드 파일과 분석 결과가 서로 다른 사진을 가리키지 않도록 묶는다.
4. 추천을 수정할 수 있고, 미분류·글자 검색 미사용 상태로도 게시할 수 있다. 인식 실패가 글 작성 전체를 막지 않는다. 얼굴 결과는 항상 사용자가 확인할 수 있게 한다.
5. 기존 기본 Post API의 JSON 배열과 필드 계약, 웹 업로드, 로그인·소유권·이미지 검증을 유지한다. 새 내용 API를 별도로 둔다.

## 현재 상태와 다음 구현의 경계

이번 변경은 설계 문서와 흐름도, 기존 안내 문서의 현재 설계 연결에 한정한다. 기존 서버·Android 코드는 사진관 버전이며 세 기능은 아직 구현하지 않았다. 과거 로컬 테스트와 3D 캡처는 새 기능의 통과 증거로 사용하지 않는다. 실제 PythonAnywhere 동작, 클라우드 Android 동기화, 최종 Word 보고서와 일부 기본 캡처도 별도 확인이 필요하다.

이 문서가 현재 설계 기준이다. 과거 `MOA_DESIGN.md`와 그 시안은 승인된 설계가 아니며, 후보 평가 원자료는 선정 과정의 이력으로 보존한다.
